## Project Overview

GameShutter is an iPad-optimized iOS app for sports video recording with in-video highlight clipping. Deployment target: iOS 12.4 (the target-level setting; the project-level 11.2 is overridden), Swift 5 — so iOS 13+ APIs (e.g. `.builtInTripleCamera`/`.builtInDualWideCamera`) must stay behind `#available(iOS 13.0, *)` checks, as the existing code does. No CocoaPods — use `.xcodeproj` directly.

**Branch lineage:** `Highlight_only` stripped the BLE gimbal/remote stack, scoreboard overlay, team config UI, and the old compass/heading display (`729c26f`) down to bare camera recording + highlights. `CourtSurvey_detection` later re-added a `CLLocationManager` heading HUD, a timed-metadata track (`mdta/com.camcourt.*`), and a YOLO-based Court Survey phase (`CourtSurveyor.swift`, `bbp_v7.mlpackage`) — **all three have since been deleted from this folder**, so the app is back to camera recording + watermark + highlights only. None of the removed code exists here: don't assume anything referencing `BLE_stack/`, `scoreBoardData`, `teamElement`, `LocationDelegate`, `CLLocationManager`, `CompassOverlayView`, `CourtSurveyor`, or a `VideoWriter` metadata input is available. **This folder has no git history** (it was removed after copying); the commits and branches named above live only in the original repo at `~/Documents/CamCourt` (remote `github.com/HenryZhang2000/CamCourt`) — look there for `git log`/`git branch` or to recover removed features.

`README.md` is a stale leftover from the upstream "MagicVideo" sample this project was forked from (claims iOS 10 / Swift 4 / torch support) — ignore it in favor of this file.

No unit tests exist. Testing is done on physical devices — camera and highlight-clip export require hardware (simulator camera feed is unusable for recording verification).

## Architecture

### Video Pipeline (`videoManager.swift`, owned by `CameraViewController` as `vManager`)

1. `setupCaptureSession()` configures an `AVCaptureSession` (`.high` preset) with a back camera (`.builtInTripleCamera` → `.builtInDualWideCamera` → `.builtInWideAngleCamera` fallback chain on iOS 13+), a front camera, and a mic input. Video output pixel format is forced to `kCVPixelFormatType_32BGRA` for CoreImage compatibility.
2. `videoManager` is the `AVCaptureVideoDataOutputSampleBufferDelegate` and `AVCaptureAudioDataOutputSampleBufferDelegate` for both outputs, each on its own queue (`Constants.QueueLabels.VideoSessionQueue` / `AudioSessionQueue`).
3. In `captureOutput(_:didOutput:from:)`: orientation is corrected via `CIImage.oriented(forExifOrientation:)` based on `isBackCameraActive` + `orientation`, then:
   - **Preview**: the corrected `CIImage` is drawn directly to a `GLKView` via `CIContext(eaglContext:)` — center-cropped to match the preview's aspect ratio.
   - **Recording**: the same `CIImage`, with the GameShutter logo composited over its bottom-right corner by `watermarked(_:)` (recording only — the preview stays clean), is rendered into a `CVPixelBuffer`, wrapped in a new `CMSampleBuffer`, and handed to `VideoWriter`. The watermark is a pre-rendered transparent PNG (`GameShutterWatermark` imageset, white lockup with baked-in shadow, regenerated by `Tools/render_watermark.swift` — not an app-target file) scaled to a fixed fraction of frame height and faded to 90%; the positioned result is cached per frame extent. Highlight clips inherit it since they're exported from the full recording. `ImageEffects.swift`'s CIFilter extensions are still unused dead code.
4. `VideoWriter` wraps `AVAssetWriter` to mux H.264 video + AAC audio into a `.mov`-typed file at `documents/video.mp4`. It defers `startSession(atSourceTime:)` until the first *video* frame arrives (avoids a leading black frame), then requires `isReadyForMoreMediaData` on both inputs before appending.
5. **Pause/resume**: `pauseRecording()`/`resumeRecording()` stop/restart the `AVCaptureSession` outright (not just the writer). `CMResumed`/`CMPausedTime`/`CMSkipTime` track the wall-clock gap and subtract it from every subsequent sample's presentation/decode timestamps, so the output video has no gap or pause artifact.
6. **Highlights**: tapping the highlight button sets `ishighLighting = true`; the next video frame captures `presentationTimeStamp - firstSamplebufTime` into `highLightArray` and resets the flag (so a tap always marks "now", not a stale timestamp). Each capture fires `videoManager.onHighlightCaptured(count)` on the main thread, which drives the orange count badge (`HighlightBadgeLabel`, a subview of the highlight button) in `CameraViewController` — it counts real captures, not taps, hides at 0, and resets to 0 on stop (`saveVideo()`) and on each new recording start; captures reported after `isCapturing` goes false are ignored so an in-flight frame can't re-show it after stop. On `stopRecording`, `generateHighLightClip()` runs one `AVAssetExportSession` per recorded timestamp against the just-finished full recording, exporting a `HighlightDuration`-second (default 10s, hardcoded — the Settings UI row for this is currently display-only and not wired up) clip ending 1s after the marked point, then saves each clip to Photos. Highlights marked less than `HighlightDuration - 1`s into the recording are skipped (the clip wouldn't fit). Completion is tracked with a `DispatchGroup` that only real exports enter, so `generateHighLightClip`'s completion fires exactly once on every path, including when every highlight is skipped. Don't go back to shared counters incremented from the concurrent export callbacks.

**Saving to Photos** (`stopRecording`): `generateHighLightClip` reads the full recording via `AVAssetExportSession` *concurrently* with the main video's own `PHAssetCreationRequest.addResource`, so that resource creation uses `shouldMoveFile = false` (copy, not move) — moving/renaming the file out from under the still-in-progress highlight reads was a real race that could silently fail the main video's save. `cleanup()` deletes the local original afterward either way. **Save-or-delete prompt**: a user-initiated Stop (after the "Are you sure?" confirm) passes `confirmSaveFullVideo` to `stopRecording`, so recording stops immediately and a "Save Full Video?" alert appears once the file is finished; Delete skips the Photos save and calls `cleanup()` only after the `highlightsDone` `DispatchGroup` signals every highlight export finished (they read the same file), and only if no new recording has started. Highlight clips are saved either way. Background/termination stops pass `nil` and always save, since no prompt can be answered. A save failure calls `videoManager.onSaveFailed` (wired to an alert in `CameraViewController`) instead of only printing to the console.

**CIImage coordinate system**: bottom-left origin (unlike UIKit). Relevant to the watermark placement (bottom-right = max x, *min* y) and any other overlay compositing.

**Single video file**: recordings always write to `documents/video.mp4`, removed and recreated on each `startRecording()` — a new recording overwrites any prior unsaved one. Highlight clips get their own UUID-named temp files that are deleted after export.

**Finish serialization**: `videoManager` keeps the video capture queue (`videoCaptureQueue`) so `stopRecording()` can dispatch `markAsFinished()`/`finish()` through it rather than calling straight from the main-thread caller — appending to an `AVAssetWriterInput` after `markAsFinished()` throws, so finishing must be serialized after any in-flight or already-enqueued `videoOutput()` call. Keep routing it through that queue (this fixed a real video-not-saved bug when per-frame work was slower).

### Zoom

Two independent zoom paths exist and both write to `vManager.deviceZoomFactor`:
- **Pinch gesture** (`CameraViewController.handlePinchGesture`): captures `device.videoZoomFactor` as `pinchStartZoomFactor` on `.began`, then scales by `pinch.scale` on `.changed`, clamped to `[minAvailableVideoZoomFactor, activeFormat.videoMaxZoomFactor]`.
- **Programmatic** (`videoManager.changeDeviceZoom(percent:)` / a duplicate in `CameraViewController`): maps a `0...1` percent to `[1, maxZoomFactor]` where `maxZoomFactor` is the *min* of front/back max zoom (so switching cameras doesn't exceed either device's range).

`deviceZoomFactor` is reapplied to whichever camera becomes active in `switchCamera()`.

### View Controllers

- `CameraViewController` — the only functional screen; owns `videoManager`, drives the record/pause/resume/highlight buttons and the elapsed-time label (`keep_timer`, ticking via `Timer.scheduledTimer`). Recording state persists across backgrounding: `appMovedToBackground` force-stops and saves; `appwillTerminate` does the same on termination.
- `settingViewController` — a single-row table: a static "Highlight Duration: 10" label, not yet connected to `vManager.HighlightDuration`. Nothing reads `UserDefaults` anymore.

### App Lifecycle

Classic `UIApplicationDelegate` lifecycle — there is no `SceneDelegate`/`UIApplicationSceneManifest`. `AppDelegate` is a near-empty stub (no BLE state-restoration handling on this branch) with a `window` property; the UI loads from `Main.storyboard` via `UIMainStoryboardFile` in Info.plist. Backgrounding/termination handling lives in `CameraViewController` via `NotificationCenter` observers, not in `AppDelegate`.

### Key Constraints

- **Landscape only** (`UISupportedInterfaceOrientations` in Info.plist) — all UI assumes landscape.
- **iPad primary target** — layout assumes a large screen, though `TARGETED_DEVICE_FAMILY = "1,2"` means the app also builds and installs on iPhone.
- **Physical device required** — camera capture and Photos export do not work in the simulator.
- **Hand-edited project file** — `objectVersion = 48` has no synchronized file groups, so adding or removing a source/resource file means adding or removing its `PBXBuildFile`, `PBXFileReference`, group, and build-phase entries in `project.pbxproj` by hand, not just touching the disk.
- **GLKView / EAGLContext** — preview rendering uses OpenGL ES 2 (deprecated since iOS 12); no overlay is composited into the live preview, only into recordings (the watermark).
